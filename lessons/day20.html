Module 3: Vocabulary (25 Technical Terms)

Encapsulation

/ɪnˌkæpsəˈleɪʃən/ • Noun

Definition: The bundling of data and methods that operate on that data within a single unit or class.

Tech "Encapsulation prevents external code from directly accessing internal object states."

Abstraction

/æbˈstrækʃən/ • Noun

Definition: Hiding complex implementation details and showing only the essential features of the object.

Tech "Through abstraction, we can interact with an object without knowing its inner workings."

Inheritance

/ɪnˈhɛrɪtəns/ • Noun

Definition: A mechanism where a new class inherits properties and behaviors from an existing class.

Tech "We used inheritance to create specific User types from a base Account class."

Polymorphism

/ˌpɒliˈmɔːrfɪzəm/ • Noun

Definition: The ability of different objects to respond, each in its own way, to identical messages.

Tech "Polymorphism allows us to call a render method on any UI component."

Cohesion

/koʊˈhiːʒən/ • Noun

Definition: The degree to which elements inside a module belong together.

Tech "We should aim for high cohesion within our microservices."

Coupling

/ˈkʌplɪŋ/ • Noun

Definition: The degree of interdependence between software modules.

Tech "Loose coupling makes the system easier to test and maintain."

Dependency

Tech "We use dependency injection to provide the database connection."

Refactoring

Modularity

/meɪnˌteɪnəˈbɪlɪti/ • Noun

Tech "Adding descriptive comments increases the maintainability of the codebase."

Testability

/tɛstəˈbɪlɪti/ • Noun

Tech "Decoupling the UI from the business logic improves testability."

Scalability

/skeɪləˈbɪlɪti/ • Noun

Tech "The microservices architecture was chosen for its scalability."

Singleton

/ˈsɪŋɡəltən/ • Noun

Definition: A creational design pattern that lets you ensure that a class has only one instance.

Tech "We use a Singleton for the database connection pool."

Observer

/əbˈzɜːrvər/ • Noun

Definition: A behavioral design pattern that lets you define a subscription mechanism to notify multiple objects.

Tech "The UI updates automatically using the Observer pattern when data changes."

Factory

/ˈfæktəri/ • Noun

Definition: A creational design pattern that provides an interface for creating objects in a superclass.

Tech "Use a Factory method to create different types of user accounts."

Decorator

/ˈdɛkəreɪtər/ • Noun

Definition: A structural design pattern that lets you attach new behaviors to objects by placing them inside special wrapper objects.

Tech "We implemented a logging Decorator for the repository."

Strategy

/ˈstrætədʒi/ • Noun

Definition: A behavioral design pattern that lets you define a family of algorithms, put each of them into a separate class, and make their objects interchangeable.

Tech "The payment processing system uses the Strategy pattern to support multiple gateways."

Repository

/rɪˈpɒzɪtəri/ • Noun

Definition: A design pattern that mediates between the domain and data mapping layers.

Tech "All database queries should be isolated in the Repository layer."

Facade

/fəˈsɑːd/ • Noun

Definition: A structural design pattern that provides a simplified interface to a library, a framework, or any other complex set of classes.

Tech "We created a Facade to interact with the legacy billing system."

Adapter

/əˈdæptər/ • Noun

Definition: A structural design pattern that allows objects with incompatible interfaces to collaborate.

Tech "Write an Adapter to translate our API responses to the format the third-party requires."

Command

/kəˈmɑːnd/ • Noun

Definition: A behavioral design pattern that turns a request into a stand-alone object that contains all information about the request.

Tech "The Command pattern is perfect for implementing undo/redo functionality."

Template

/ˈtɛmplɪt/ • Noun

Definition: A behavioral design pattern that defines the skeleton of an algorithm in the superclass but lets subclasses override specific steps.

Tech "The Template Method pattern works well for our report generation workflow."

Bridge

/brɪdʒ/ • Noun

Definition: A structural design pattern that lets you split a large class into two separate hierarchies—abstraction and implementation.

Tech "Using the Bridge pattern avoided an explosion of subclasses for rendering shapes on different OS platforms."

Composition

/ˌkɒmpəˈzɪʃən/ • Noun

Definition: A design principle where classes achieve polymorphic behavior and code reuse by containing instances of other classes instead of inheriting from them.

Tech "Favor composition over inheritance to make the system more flexible."

Module 4: Phrasal Verbs (Code Refactoring Context)

Break down

Meaning: To divide a large system or complex problem into smaller, manageable parts.

  • Tech "Let's break down this monolithic class into several smaller components."

Factor out

Meaning: To extract a common piece of logic into a separate method or class.

  • Tech "We should factor out this validation logic into a utility class."

Wrap up

Meaning: To encapsulate or enclose a process, often referring to a facade or a wrapper.

  • Tech "Let's wrap up this legacy API call so it's easier to use."

Pull out

  • Tech "We need to pull out the configuration settings into an environment file."

  • Tech "The Builder pattern helps us build up this complex object step by step."

Hook up

  • Tech "Once the frontend is ready, we can hook it up to the new backend API."

Tie together

  • Tech "The facade pattern ties together all these underlying subsystems."

Module 6: Grammar — Diplomatic Feedback Language

Concept: Code reviews can easily sound harsh or critical. Using diplomatic language softens the feedback, focuses on the code rather than the person, and opens a discussion rather than issuing a command.

Instead of: "You did this wrong. Change it."
Use: "I noticed that... You might consider..."
  • "You might consider..." (Soft suggestion) - "You might consider extracting this logic into a separate helper."
  • "One approach could be..." (Offering alternatives) - "One approach could be using the Strategy pattern here."
  • "I noticed that..." (Observational, non-accusatory) - "I noticed that this loop runs in O(N^2) time."
  • "It would be worth exploring..." (Encouraging research/change) - "It would be worth exploring if we can cache these results."
  • "Have you thought about..." (Questioning rather than telling) - "Have you thought about how this handles null inputs?"
  • "A potential improvement here would be..." (Focusing on the code quality) - "A potential improvement here would be renaming these variables for clarity."
Direct/Harsh: Why did you write this huge method? Break it up.
Diplomatic: I noticed this method handles multiple responsibilities. Have you thought about breaking it down to improve cohesion?

Module 8: Role-Play Conversations

1. Code review feedback to a junior

Junior: I pushed the new feature. It works perfectly!
You: Great job getting it working! I noticed that the user validation logic is inside the UI component. You might consider extracting it to a service class to improve reusability.
Junior: Oh, I see. I'll move it to a service class.

2. SOLID explanation to an intern

Intern: Why do we need so many small classes instead of one big one?
You: It's about the Single Responsibility Principle. When a class has only one reason to change, it's much easier to maintain and less likely to break other parts of the system when we update it.

3. Design pattern justification to a tech lead

Tech Lead: Why did you introduce an Adapter pattern here? It seems like overkill.
You: I understand the concern. One approach could be direct integration, but the Adapter isolates our core logic from the third-party API changes. It gives us a solid foundation if we swap vendors later.

4. Refactoring proposal to a manager

Manager: We need to ship the new billing feature this week. Can we skip the refactoring?
You: If we skip it, the technical debt will slow down all future billing updates. A potential improvement here would be to dedicate just one day to decouple the old code, which will actually make testing the new feature faster.

5. Complex PR comment discussion

Peer: I don't agree with your PR comment about using the Strategy pattern. My way is simpler.
You: Your way definitely works and keeps it simple for now. My thought was about scaling up later when we add more payment types. Let's hop on a quick call to discuss the best of both worlds.

Module 10: Reading Practice

Why Design Patterns Still Matter in Modern Software Engineering

In the fast-paced world of modern software engineering, where new frameworks and languages emerge constantly, some developers argue that classic design patterns are obsolete. They suggest that functional programming paradigms or modern framework conventions have replaced the need for the Gang of Four patterns.

However, this perspective overlooks the fundamental purpose of design patterns. Patterns are not just templates for code; they are a shared vocabulary for developers. When an engineer mentions a "Factory" or an "Observer," it immediately conveys a complex architectural concept without requiring a lengthy explanation of the underlying logic.

Design patterns provide a solid foundation for addressing recurring problems in software design. Even when using a modern JavaScript framework, concepts like the Singleton pattern (for state management stores) or the Decorator pattern (for higher-order components) are heavily utilized, even if the terminology slightly shifts.

Understanding these patterns helps developers navigate complex codebases and write highly maintainable systems. It encourages a focus on separation of concerns, loose coupling, and high cohesion. While it is true that one shouldn't forcefully shoehorn a pattern into every problem—adhering to the "Keep it Simple" principle—knowing when and where to apply them is a hallmark of a senior engineer.

Ultimately, design patterns are a tool for managing complexity. As systems scale up and technical debt threatens to slow down development, relying on proven, structured approaches ensures that the software remains robust. They allow us to stand on the shoulders of giants, learning from decades of software architecture experience rather than reinventing the wheel with every new project.

Module 14: Technical Communication

Concept: Explain SOLID principles with one concrete software example per letter.

S - Single Responsibility Principle

A class should have one reason to change. Example: A `UserAuthenticator` class handles login, while a separate `UserMailer` class handles sending welcome emails.

O - Open/Closed Principle

Open for extension, closed for modification. Example: Adding a new payment method by creating a new `PayPalProcessor` class that implements a `PaymentGateway` interface, without changing the core `CheckoutService`.

L - Liskov Substitution Principle

Subtypes must be substitutable for their base types. Example: If `Bird` has a `fly()` method, an `Ostrich` subclass violates this. Instead, have a `FlyingBird` interface.

I - Interface Segregation Principle

Clients shouldn't be forced to depend on interfaces they don't use. Example: Splitting a massive `IPrinter` interface into `IPrint`, `IScan`, and `IFax` so a simple printer doesn't have to implement scan methods.

D - Dependency Inversion Principle

Depend on abstractions, not concretions. Example: Injecting a generic `IDatabase` interface into a service constructor rather than instantiating a specific `MySQLDatabase` inside it.

Module 15: Group Discussion

Topic: "Clean Code vs Working Code: Which Should Be Priority?"

Opening Statement: Working code delivers immediate business value, but without clean code, future business value is jeopardized.

Supporting Points (Working Code):

  • Startups need to ship fast to survive; perfect architecture delays time-to-market.
  • You can always refactor working code, but clean code that doesn't solve the user's problem is useless.

Counter-arguments (Clean Code):

  • "Quick and dirty" code becomes technical debt immediately.
  • Bad architecture slows down all subsequent features, ultimately hurting speed.

Conclusion: The balance depends on the project lifecycle phase, but a minimum baseline of clean, maintainable code is always required.

Useful Vocab: Technical Debt, Time-to-market, Maintainability, Refactoring phase.

Module 18: Common Indian English Mistakes (OOP & Code Review)

Wrong: "I will suggest you to change this pattern."
Correct: "I suggest changing this pattern." or "I suggest you change this pattern."
Explanation: 'Suggest' is not followed by an object pronoun and an infinitive.
Wrong: "We are using singleton pattern from a long time."
Correct: "We have been using the singleton pattern for a long time."
Explanation: Use 'for' to indicate duration, and present perfect continuous for an action starting in the past and continuing.
Wrong: "Please do the needful to refactor the code."
Correct: "Please refactor the code."
Explanation: "Do the needful" is archaic and sounds unnatural in global tech environments.
Wrong: "I have a doubt in this pull request."
Correct: "I have a question about this pull request."
Explanation: In global English, 'doubt' implies suspicion or disbelief, while 'question' means you need clarification.
Wrong: "Can you revert back on my review comments?"
Correct: "Can you reply to my review comments?"
Explanation: 'Revert' means to return to a previous state (like git revert), not to reply. Also, 'revert back' is redundant.
Wrong: "This code is working fine only."
Correct: "This code is working fine."
Explanation: Adding 'only' for emphasis at the end of a sentence is a direct translation from Hindi/regional languages.
Wrong: "Let us discuss about the architecture."
Correct: "Let us discuss the architecture."
Explanation: 'Discuss' is a transitive verb and does not take the preposition 'about'.
Wrong: "The class is comprising of multiple methods."
Correct: "The class comprises multiple methods."
Explanation: 'Comprise' does not take 'of'. (Alternatively: 'is composed of').
Wrong: "He didn't approved the PR."
Correct: "He didn't approve the PR."
Explanation: After 'did' or 'didn't', always use the base form of the verb.
Wrong: "I am having 5 years of experience in OOP."
Correct: "I have 5 years of experience in OOP."
Explanation: 'Have' showing possession/state is not used in the continuous form.

Module 6: Grammar — Diplomatic Feedback Language

Concept: Code reviews can easily sound harsh or critical. Using diplomatic language softens the feedback, focuses on the code rather than the person, and opens a discussion rather than issuing a command.

Instead of: "You did this wrong. Change it."
Use: "I noticed that... You might consider..."
  • "You might consider..." (Soft suggestion) - "You might consider extracting this logic into a separate helper."
  • "One approach could be..." (Offering alternatives) - "One approach could be using the Strategy pattern here."
  • "I noticed that..." (Observational, non-accusatory) - "I noticed that this loop runs in O(N^2) time."
  • "It would be worth exploring..." (Encouraging research/change) - "It would be worth exploring if we can cache these results."
  • "Have you thought about..." (Questioning rather than telling) - "Have you thought about how this handles null inputs?"
  • "A potential improvement here would be..." (Focusing on the code quality) - "A potential improvement here would be renaming these variables for clarity."
Direct/Harsh: Why did you write this huge method? Break it up.

Module 10: Reading Practice

Why Design Patterns Still Matter in Modern Software Engineering

In the fast-paced world of modern software engineering, where new frameworks and languages emerge constantly, some developers argue that classic design patterns are obsolete. They suggest that functional programming paradigms or modern framework conventions have replaced the need for the Gang of Four patterns.

However, this perspective overlooks the fundamental purpose of design patterns. Patterns are not just templates for code; they are a shared vocabulary for developers. When an engineer mentions a "Factory" or an "Observer," it immediately conveys a complex architectural concept without requiring a lengthy explanation of the underlying logic.

Design patterns provide a solid foundation for addressing recurring problems in software design. Even when using a modern JavaScript framework, concepts like the Singleton pattern (for state management stores) or the Decorator pattern (for higher-order components) are heavily utilized, even if the terminology slightly shifts.

Understanding these patterns helps developers navigate complex codebases and write highly maintainable systems. It encourages a focus on separation of concerns, loose coupling, and high cohesion. While it is true that one shouldn't forcefully shoehorn a pattern into every problem—adhering to the "Keep it Simple" principle—knowing when and where to apply them is a hallmark of a senior engineer.

Ultimately, design patterns are a tool for managing complexity. As systems scale up and technical debt threatens to slow down development, relying on proven, structured approaches ensures that the software remains robust. They allow us to stand on the shoulders of giants, learning from decades of software architecture experience rather than reinventing the wheel with every new project.

Module 14: Technical Communication

Concept: Explain SOLID principles with one concrete software example per letter.

S - Single Responsibility Principle

A class should have one reason to change. Example: A `UserAuthenticator` class handles login, while a separate `UserMailer` class handles sending welcome emails.

O - Open/Closed Principle

Open for extension, closed for modification. Example: Adding a new payment method by creating a new `PayPalProcessor` class that implements a `PaymentGateway` interface, without changing the core `CheckoutService`.

L - Liskov Substitution Principle

Subtypes must be substitutable for their base types. Example: If `Bird` has a `fly()` method, an `Ostrich` subclass violates this. Instead, have a `FlyingBird` interface.

I - Interface Segregation Principle

Clients shouldn't be forced to depend on interfaces they don't use. Example: Splitting a massive `IPrinter` interface into `IPrint`, `IScan`, and `IFax` so a simple printer doesn't have to implement scan methods.

D - Dependency Inversion Principle

Depend on abstractions, not concretions. Example: Injecting a generic `IDatabase` interface into a service constructor rather than instantiating a specific `MySQLDatabase` inside it.

Module 18: Common Indian English Mistakes (OOP & Code Review)

Wrong: "I will suggest you to change this pattern."
Correct: "I suggest changing this pattern." or "I suggest you change this pattern."
Explanation: 'Suggest' is not followed by an object pronoun and an infinitive.
Wrong: "We are using singleton pattern from a long time."
Correct: "We have been using the singleton pattern for a long time."
Explanation: Use 'for' to indicate duration, and present perfect continuous for an action starting in the past and continuing.
Wrong: "Please do the needful to refactor the code."
Correct: "Please refactor the code."
Explanation: "Do the needful" is archaic and sounds unnatural in global tech environments.
Wrong: "I have a doubt in this pull request."
Correct: "I have a question about this pull request."
Explanation: In global English, 'doubt' implies suspicion or disbelief, while 'question' means you need clarification.
Wrong: "Can you revert back on my review comments?"
Correct: "Can you reply to my review comments?"
Explanation: 'Revert' means to return to a previous state (like git revert), not to reply. Also, 'revert back' is redundant.
Wrong: "This code is working fine only."
Correct: "This code is working fine."
Explanation: Adding 'only' for emphasis at the end of a sentence is a direct translation from Hindi/regional languages.
Wrong: "Let us discuss about the architecture."
Correct: "Let us discuss the architecture."
Explanation: 'Discuss' is a transitive verb and does not take the preposition 'about'.
Wrong: "The class is comprising of multiple methods."
Correct: "The class comprises multiple methods."
Explanation: 'Comprise' does not take 'of'. (Alternatively: 'is composed of').
Wrong: "He didn't approved the PR."
Correct: "He didn't approve the PR."
Explanation: After 'did' or 'didn't', always use the base form of the verb.
Wrong: "I am having 5 years of experience in OOP."

Explanation: 'Have' showing possession/state is not used in the continuous form.

Concept: Code reviews can easily sound harsh or critical. Using diplomatic language softens the feedback, focuses on the code rather than the person, and opens a discussion rather than issuing a command.

Instead of: "You did this wrong. Change it."

Module 10: Reading Practice

Why Design Patterns Still Matter in Modern Software Engineering

In the fast-paced world of modern software engineering, where new frameworks and languages emerge constantly, some developers argue that classic design patterns are obsolete. They suggest that functional programming paradigms or modern framework conventions have replaced the need for the Gang of Four patterns.

However, this perspective overlooks the fundamental purpose of design patterns. Patterns are not just templates for code; they are a shared vocabulary for developers. When an engineer mentions a "Factory" or an "Observer," it immediately conveys a complex architectural concept without requiring a lengthy explanation of the underlying logic.

Design patterns provide a solid foundation for addressing recurring problems in software design. Even when using a modern JavaScript framework, concepts like the Singleton pattern (for state management stores) or the Decorator pattern (for higher-order components) are heavily utilized, even if the terminology slightly shifts.

Understanding these patterns helps developers navigate complex codebases and write highly maintainable systems. It encourages a focus on separation of concerns, loose coupling, and high cohesion. While it is true that one shouldn't forcefully shoehorn a pattern into every problem—adhering to the "Keep it Simple" principle—knowing when and where to apply them is a hallmark of a senior engineer.

Ultimately, design patterns are a tool for managing complexity. As systems scale up and technical debt threatens to slow down development, relying on proven, structured approaches ensures that the software remains robust. They allow us to stand on the shoulders of giants, learning from decades of software architecture experience rather than reinventing the wheel with every new project.

Module 14: Technical Communication

Concept: Explain SOLID principles with one concrete software example per letter.

S - Single Responsibility Principle

A class should have one reason to change. Example: A `UserAuthenticator` class handles login, while a separate `UserMailer` class handles sending welcome emails.

O - Open/Closed Principle

Open for extension, closed for modification. Example: Adding a new payment method by creating a new `PayPalProcessor` class that implements a `PaymentGateway` interface, without changing the core `CheckoutService`.

L - Liskov Substitution Principle

Subtypes must be substitutable for their base types. Example: If `Bird` has a `fly()` method, an `Ostrich` subclass violates this. Instead, have a `FlyingBird` interface.

I - Interface Segregation Principle

Clients shouldn't be forced to depend on interfaces they don't use. Example: Splitting a massive `IPrinter` interface into `IPrint`, `IScan`, and `IFax` so a simple printer doesn't have to implement scan methods.

D - Dependency Inversion Principle

Depend on abstractions, not concretions. Example: Injecting a generic `IDatabase` interface into a service constructor rather than instantiating a specific `MySQLDatabase` inside it.

Module 18: Common Indian English Mistakes (OOP & Code Review)

Wrong: "I will suggest you to change this pattern."
Correct: "I suggest changing this pattern." or "I suggest you change this pattern."
Explanation: 'Suggest' is not followed by an object pronoun and an infinitive.
Wrong: "We are using singleton pattern from a long time."
Correct: "We have been using the singleton pattern for a long time."
Explanation: Use 'for' to indicate duration, and present perfect continuous for an action starting in the past and continuing.
Wrong: "Please do the needful to refactor the code."
Correct: "Please refactor the code."
Explanation: "Do the needful" is archaic and sounds unnatural in global tech environments.
Wrong: "I have a doubt in this pull request."
Correct: "I have a question about this pull request."
Explanation: In global English, 'doubt' implies suspicion or disbelief, while 'question' means you need clarification.
Wrong: "Can you revert back on my review comments?"
Correct: "Can you reply to my review comments?"
Explanation: 'Revert' means to return to a previous state (like git revert), not to reply. Also, 'revert back' is redundant.
Wrong: "This code is working fine only."
Correct: "This code is working fine."
Explanation: Adding 'only' for emphasis at the end of a sentence is a direct translation from Hindi/regional languages.
Wrong: "Let us discuss about the architecture."
Correct: "Let us discuss the architecture."
Explanation: 'Discuss' is a transitive verb and does not take the preposition 'about'.
Wrong: "The class is comprising of multiple methods."
Correct: "The class comprises multiple methods."
Explanation: 'Comprise' does not take 'of'. (Alternatively: 'is composed of').
Wrong: "He didn't approved the PR."
Correct: "He didn't approve the PR."
Explanation: After 'did' or 'didn't', always use the base form of the verb.
Wrong: "I am having 5 years of experience in OOP."

  • "Have you thought about..." (Questioning rather than telling) - "Have you thought about how this handles null inputs?"
  • "A potential improvement here would be..." (Focusing on the code quality) - "A potential improvement here would be renaming these variables for clarity."

Module 10: Reading Practice

Why Design Patterns Still Matter in Modern Software Engineering

In the fast-paced world of modern software engineering, where new frameworks and languages emerge constantly, some developers argue that classic design patterns are obsolete. They suggest that functional programming paradigms or modern framework conventions have replaced the need for the Gang of Four patterns.

However, this perspective overlooks the fundamental purpose of design patterns. Patterns are not just templates for code; they are a shared vocabulary for developers. When an engineer mentions a "Factory" or an "Observer," it immediately conveys a complex architectural concept without requiring a lengthy explanation of the underlying logic.

Design patterns provide a solid foundation for addressing recurring problems in software design. Even when using a modern JavaScript framework, concepts like the Singleton pattern (for state management stores) or the Decorator pattern (for higher-order components) are heavily utilized, even if the terminology slightly shifts.

Understanding these patterns helps developers navigate complex codebases and write highly maintainable systems. It encourages a focus on separation of concerns, loose coupling, and high cohesion. While it is true that one shouldn't forcefully shoehorn a pattern into every problem—adhering to the "Keep it Simple" principle—knowing when and where to apply them is a hallmark of a senior engineer.

Ultimately, design patterns are a tool for managing complexity. As systems scale up and technical debt threatens to slow down development, relying on proven, structured approaches ensures that the software remains robust. They allow us to stand on the shoulders of giants, learning from decades of software architecture experience rather than reinventing the wheel with every new project.

Module 14: Technical Communication

Concept: Explain SOLID principles with one concrete software example per letter.

S - Single Responsibility Principle

A class should have one reason to change. Example: A `UserAuthenticator` class handles login, while a separate `UserMailer` class handles sending welcome emails.

O - Open/Closed Principle

Open for extension, closed for modification. Example: Adding a new payment method by creating a new `PayPalProcessor` class that implements a `PaymentGateway` interface, without changing the core `CheckoutService`.

L - Liskov Substitution Principle

Subtypes must be substitutable for their base types. Example: If `Bird` has a `fly()` method, an `Ostrich` subclass violates this. Instead, have a `FlyingBird` interface.

I - Interface Segregation Principle

Clients shouldn't be forced to depend on interfaces they don't use. Example: Splitting a massive `IPrinter` interface into `IPrint`, `IScan`, and `IFax` so a simple printer doesn't have to implement scan methods.

D - Dependency Inversion Principle

Depend on abstractions, not concretions. Example: Injecting a generic `IDatabase` interface into a service constructor rather than instantiating a specific `MySQLDatabase` inside it.

Module 18: Common Indian English Mistakes (OOP & Code Review)

Wrong: "I will suggest you to change this pattern."
Correct: "I suggest changing this pattern." or "I suggest you change this pattern."
Explanation: 'Suggest' is not followed by an object pronoun and an infinitive.
Wrong: "We are using singleton pattern from a long time."
Correct: "We have been using the singleton pattern for a long time."
Explanation: Use 'for' to indicate duration, and present perfect continuous for an action starting in the past and continuing.
Wrong: "Please do the needful to refactor the code."
Correct: "Please refactor the code."
Explanation: "Do the needful" is archaic and sounds unnatural in global tech environments.
Wrong: "I have a doubt in this pull request."
Correct: "I have a question about this pull request."
Explanation: In global English, 'doubt' implies suspicion or disbelief, while 'question' means you need clarification.
Wrong: "Can you revert back on my review comments?"
Correct: "Can you reply to my review comments?"
Explanation: 'Revert' means to return to a previous state (like git revert), not to reply. Also, 'revert back' is redundant.
Wrong: "This code is working fine only."
Correct: "This code is working fine."
Explanation: Adding 'only' for emphasis at the end of a sentence is a direct translation from Hindi/regional languages.
Wrong: "Let us discuss about the architecture."
Correct: "Let us discuss the architecture."
Explanation: 'Discuss' is a transitive verb and does not take the preposition 'about'.
Wrong: "The class is comprising of multiple methods."
Correct: "The class comprises multiple methods."
Explanation: 'Comprise' does not take 'of'. (Alternatively: 'is composed of').
Wrong: "He didn't approved the PR."
Correct: "He didn't approve the PR."
Explanation: After 'did' or 'didn't', always use the base form of the verb.
Wrong: "I am having 5 years of experience in OOP."
Correct: "I have 5 years of experience in OOP."
Explanation: 'Have' showing possession/state is not used in the continuous form.
